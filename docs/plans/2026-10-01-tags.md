# Tags d'équipe sur les contenus

> **Suivi** : ledger `API-59` (modèle, contrat, filtres, migration), `WEB-40` (site), `MOB-39`
> (application) ; l'import des tags biketeam referme la part « tags » de `MIG-6`.
>
> Écrit le 1er octobre 2026 à partir d'une série de questions-réponses. Ce document fixe le
> **besoin** et les décisions produit ; les choix techniques marqués « proposé » restent à
> l'implémenteur. Les points d'abord laissés ouverts ont été tranchés le même jour (§9).

## 1. Origine

- Backlog P1, *Content System* : « Tags on Ride, Post, Trip, Route, Ad — Filtering/discovery (one
  tag set per type) ».
- Biketeam n'a de tags que sur les parcours (`map_tags`, chaînes libres, vocabulaire déduit par
  `SELECT DISTINCT`, filtre en OU, tags par défaut d'équipe servant à la fois de filtre implicite et
  de pré-remplissage). L'instantané de migration exporte déjà `maps[].tags` (plan de migration
  biketeam, décision 14), que Pédalons ignore aujourd'hui (`MIG-6`).

## 2. Décisions

| # | Sujet | Décision |
|---|---|---|
| D1 | Périmètre | Les **cinq types** : sortie, publication (post), voyage, parcours, annonce. |
| D2 | Vocabulaire | **Table de tags par équipe**, pas de chaînes libres sur les contenus. |
| D3 | Jeu par type | **Un jeu distinct par type**, le type étant `RIDE`, `POST`, `TRIP`, `ROUTE`, `AD` (les trois premiers reprennent `PublicationType`). Un tag `RIDE` ne s'applique pas à un post. |
| D4 | Création / gestion du vocabulaire | **Admins d'équipe seulement** (`TeamRole.ADMIN`), et **uniquement depuis l'écran d'admin** : aucun formulaire de contenu ne crée de tag, même pour un admin. |
| D5 | Étiquetage d'un contenu | **Exactement les droits d'édition du contenu**, sans cas particulier : qui peut le modifier (auteur, organisateur, admin selon le type) pose et retire n'importe lequel de ses tags, en choisissant parmi les tags existants. Les tags font partie de la requête d'édition, pas d'un endpoint à part. |
| D6 | Filtre multi-tags | **OU** : un contenu sort s'il porte au moins un des tags demandés. |
| D7 | Listes multi-équipes | **Pas de filtre par tag** hors d'une équipe (`/api/routes`, `/api/publications`, annonces de proximité…) ; les tags y sont seulement affichés. |
| D8 | Tags par défaut d'équipe | **Non**. Pas d'équivalent de `defaultSearchTags`, ni filtre implicite ni pré-remplissage. |
| D9 | Attributs d'un tag | Libellé + **couleur**. Ni description ni ordre manuel : ordre alphabétique. |
| D10 | Couleur | Une des **9 familles** de `contracts/brand-colors.yaml` (`indigo, blue, green, red, yellow, orange, grape, teal, gray`), rendue **sous une autre forme que les badges métier** (proposé : pastille colorée + libellé en texte neutre), pour qu'un tag vert ne se lise pas « Publié ». |
| D11 | Suppression d'un tag utilisé | **Détaché partout**, après confirmation qui affiche le nombre de contenus concernés. Suppression réelle (pas de corbeille). |
| D12 | Opérations d'admin | Créer, **renommer**, **recolorer**, supprimer ; **compteur d'usage** par tag. Pas de fusion. |
| D13 | Fil mixte | Le fil d'équipe (`/api/teams/{t}/publications`, sorties + posts + voyages) **n'a pas** de filtre par tag ; les listes dédiées (sorties, posts, voyages, parcours, annonces) l'ont. |
| D14 | Modèles de sortie | Un `RideTemplate` porte des tags `RIDE`, **copiés** sur la sortie à sa création, modifiables ensuite. |
| D15 | Héritage parcours → sortie/étape | **Aucun**. Les tags `ROUTE` restent sur le parcours, visibles via la carte du parcours. |
| D16 | Bornes | Libellé ≤ **32** caractères (après trim, non vide), ≤ **10** tags par contenu, ≤ **100** tags par équipe et par type. Vérifiées côté API. |
| D17 | Unicité | Libellé unique par (équipe, type), **insensible à la casse** après trim. |
| D18 | Filtre dans l'URL | Oui, **par id de tag** : `?tags=<id>,<id>`. Stable au renommage ; un id inconnu est ignoré. |
| D19 | Affichage | **Cartes de liste** (2-3 tags puis « +n ») **et fiche** (tous) ; visibles des visiteurs anonymes, donc rendus en SSR. |
| D20 | Clients V1 | **Web** complet (affichage, filtre, étiquetage, admin du vocabulaire). **Mobile** : affichage + filtre seulement. Karoo / Garmin : rien. |
| D21 | Migration biketeam | **Import** des tags de parcours : un tag `ROUTE` par libellé distinct (trim, insensible à la casse, première graphie rencontrée gardée), couleur `gray`, idempotent au rejeu. |
| D22 | Ordre de livraison | `API-59` (avec l'import) est livré **avant les bascules de production**. Aucun rattrapage n'est prévu pour une équipe basculée avant : biketeam ne lui propose plus la migration (`AdminTeamPedalonsController`, `!team.isPedalonsMigrated()`). Les équipes de staging se recréent par `reset` ; si l'ordre ne tient pas en production, la perte des tags est acceptée. |
| D23 | Notifications | Un changement de tags **ne notifie pas**. Rien à faire : `RIDE_UPDATED` ne part que pour `NotificationChange.DATE_TIME` et `START_PLACE` — ne pas y ajouter les tags. |

## 3. Modèle (proposé)

- `Tag` (étend `BaseEntity`, **pas** `TeamEntity` : pas de corbeille, D11) : `team`, `type`
  (enum `TagTarget` — `RIDE`, `POST`, `TRIP`, `ROUTE`, `AD`), `label`, `color` (enum `TagColor`, les
  9 familles). Index unique sur `(team_id, type, lower(label))`.
- Liaison : une table d'association par entité porteuse, ou une table unique
  `content_tag(tag_id, content_id)` — au choix de l'implémenteur ; la contrainte « le type du tag
  correspond au type du contenu » est vérifiée par le service, et un contenu ne peut porter qu'un
  tag de **sa** équipe.
- `RideTemplate` porte ses tags `RIDE` de la même façon (D14).
- Multi-tenancy : le tag est rattaché à l'équipe, donc au domaine ; toute requête sur les tags filtre
  par `domainId` comme le reste.
- Migration Flyway compatible avec la version précédente (déploiement rolling) : tables nouvelles
  seulement.

## 4. Contrat d'API (proposé)

- **Vocabulaire** : `GET /api/teams/{teamSlug}/tags?type=ROUTE` → liste triée par libellé, avec
  `usageCount` (D12) — lecture ouverte à qui voit l'équipe ; `POST`, `PATCH /{tagId}` (libellé,
  couleur), `DELETE /{tagId}` → admins seulement (D4). La réponse du `DELETE` ou un `GET` préalable
  donne le nombre de contenus détachés (D11).
- **DTO** : `TagDto { id, label, color }` ajouté à la **liste et au détail** de chaque type
  (`RideDto`, `PostDto`, `TripDto`, `RouteDto`, `AdDto`, et leurs résumés de liste), ainsi qu'à
  `RideTemplateDto`.
- **Écriture** : les requêtes de création/modification de chaque type acceptent `tagIds: string[]`
  (≤ 10, tous de l'équipe et du bon type, sinon 400).
- **Filtre** : `tags=<id>,<id>` sur les listes d'équipe dédiées — `rides`, `posts`, `trips`,
  `routes`, `classifieds` sous `/api/teams/{teamSlug}/` — en OU (D6), sans doublon de résultat
  (`EXISTS` plutôt que jointure). Absent des listes multi-équipes et du fil mixte (D7, D13).
- Contrat modifié : bump de `pedalons.api.version` (mineur, ajouts seulement), skill
  `contract-first-api`.

**Invariant à tenir** : les tags d'une page de liste se résolvent **par page**, jamais par ligne —
un `TagLookup` sur le modèle de `ParticipationLookup` / `CommentCountLookup`, couvert par un
`…QueryCountTest`.

## 5. Web (`WEB-40`)

- Composant de tag commun (D10), réutilisé en carte (tronqué, « +n ») et en fiche.
- Filtre multi-sélection par tag dans chaque liste d'équipe dédiée, synchronisé avec `?tags=`
  (D18) ; liste vide de tags pour le type ⇒ pas de filtre affiché.
- Formulaires d'édition des cinq types et du modèle de sortie : sélection parmi les tags existants,
  jamais de création (D4) ; si le type n'a aucun tag, le champ renvoie un admin vers l'écran d'admin.
- Écran d'admin d'équipe : un onglet par type, création / renommage / couleur / suppression avec
  compteur d'usage et confirmation.
- Pages publiques SSR : les tags sont dans le rendu (D19).

## 6. Mobile (`MOB-39`)

- Affichage en carte et en fiche, même forme que le web (D10, couleurs via les familles déjà
  rendues par `PdlFamily`).
- Filtre par tag dans les listes d'équipe dédiées. Pas d'étiquetage ni d'admin (D20).

## 7. Migration biketeam (`MIG-6`, part « tags »)

- `SnapshotBiketeamSource` transmet déjà `BtMap.tags`. À l'import d'un parcours : normaliser
  (trim, vides écartés), retrouver ou créer le `Tag` `ROUTE` de l'équipe par libellé insensible à la
  casse (couleur `gray`), puis remplacer l'ensemble des tags du parcours.
- Rejeu idempotent : aucun doublon de tag ni de liaison.
- Au-delà de 10 tags sur un parcours ou de 100 tags dans l'équipe (D16) : garder les premiers dans
  l'ordre de l'instantané et le journaliser, plutôt que faire échouer la migration.
- `defaultSearchTags` n'est ni exporté ni importé (D8).

## 8. Tests attendus

- Backend : unicité insensible à la casse, bornes D16, type du tag ≠ type du contenu ⇒ 400, tag
  d'une autre équipe ⇒ 400, droits admin sur le vocabulaire, détachement à la suppression, filtre OU
  sans doublon, copie modèle → sortie, `TagLookup` en nombre de requêtes fixe par page, import
  biketeam idempotent avec fusion de casse.
- Web : e2e « l'admin crée un tag, un membre l'appose, la liste filtrée par URL le retrouve ».

## 9. Points tranchés après coup

Laissés ouverts à la première rédaction, tranchés le 1er octobre 2026 :

- **P1** — Création à la volée depuis le formulaire d'un contenu : **non**, écran d'admin seulement
  (D4).
- **P2** — Équipes déjà basculées : livrer avant les bascules de production (D22).
- **P3** — Retrait d'un tag par un éditeur non admin : les tags suivent exactement les droits
  d'édition du contenu (D5).
- **P4** — Notifications : aucune, et aucun travail (D23).
